1. Executive Summary & Concurrency Milestones

This report presents the empirical findings of pushing a production Node.js, Redis, and MongoDB e-commerce catalog backend to the absolute hardware and operating system boundary: 20,000 concurrent Virtual Users (VUs) on a single machine.

In earlier phases, scaling was limited by MongoDB table scans (98.46% collapse at 10k VUs) and later by MongoDB disk IOPS queueing (1.03% query drops at 15k VUs). Introducing Redis Cache-Aside with Distributed Mutex Locks conquered 15,000 VUs. However, jumping to 20,000 concurrent users exposed deeper layers of physical contention: OS ephemeral port exhaustion, loopback TCP socket contention, and V8 JSON serialization churn.

By implementing Two-Tier L1/L2 Caching (In-Process V8 Heap RAM + Centralized Redis), tuning kernel socket backlogs (somaxconn=4096), and expanding ephemeral port ranges (portrange.first=10240), the backend delivered 2,868,574 requests at 7,319 RPS with 0.00% error rate and 1.42ms p(95) tail latency.

2. The 5 Chronological Bottlenecks & Root-Cause Analyses

Real-world systems engineering is iterative: solving one layer exposes the next hidden bottleneck. Here is the chronological progression documented in v2-with-redis/bottlenecks/:

Step 01: 10k Baseline Failure Analysis (Unindexed MongoDB Collapse)

Failure Mode: When tested against 10k VUs, a single Node.js worker and unindexed MongoDB collapsed instantly with a 98.46% failure rate. The MongoDB engine locked at 100% CPU executing table scans (COLLSCAN) across 500,000 documents.
Resolution: Engineered Compound Equality-Sort-Range (ESR) index { category: 1, price: 1, _id: 1 } and bypassed Mongoose document hydration using .lean(), achieving totalDocsExamined: 0.

Step 02: 20k Concurrency Limits (macOS Ephemeral Port Exhaustion)

Failure Mode: Jumping straight to 20,000 VUs caused k6 to crash with can't assign requested address (EADDRNOTAVAIL), dropping 109,240 packets (7.52% error rate).
Root Cause: macOS assigns outbound ephemeral ports from 49,152 to 65,535 (only 16,383 available sockets). When 20,000 concurrent VUs opened connections, the OS exhausted its entire port pool.
Resolution: Expanded ephemeral ports via kernel sysctl: sudo sysctl -w net.inet.ip.portrange.first=10240 (unlocking 55,295 ports).

Step 03: 15k Clustering Milestone (MongoDB Disk IOPS Bottleneck)

Failure Mode: Running 10 clustered Node.js workers directly against MongoDB sustained 1.51M requests, but suffered a 1.03% query timeout rate at peak load.
Root Cause: While covered queries avoided document scans, 3,869 queries per second saturated the WiredTiger disk queue and memory cache.
Resolution: Introduced Redis Cache-Aside with distributed mutex locking and TTL jittering to offload 95%+ of query volume from the database.

Step 04: 15k Clustered Redis Benchmark (15k Conquered)

Outcome: Redis eliminated all database queueing. Handled 1,958,211 requests at 5,000 RPS with 0.00% error rate, 292 µs median latency, and MongoDB CPU dropped to under 1%.

Step 05: 20k Tail-Latency & Co-Location Loopback Bottleneck

Failure Mode: Re-testing at 20,000 VUs with Redis eliminated dropped packets (0.00% errors across 1.83M requests), but tail latency crossed SLA thresholds: p(95)=2.02s vs. target < 1000ms.
Root Causes Diagnosed:

  1. Single-Host Loopback Contention: Running k6 + 10 Node workers + Redis + 2 MongoDB instances on the same 10 cores resulted in over 40,000 concurrent TCP sockets. Activity Monitor revealed the macOS kernel burning 65.76% System CPU managing 5,270 threads.
  2. Double-Serialization V8 Churn: Deserializing Redis strings with JSON.parse() and reserializing with Express res.json() allocated 36.6 Million objects on the V8 heap, causing frequent garbage collection pauses.
  3. Socket Accept Backlog Overflow: Default macOS listen backlog was capped at 128 connections.
Ephemeral Port Expansion: 49,152 ➔ 10,240 (55k ports)
Socket Backlog Expansion: 128 ➔ 4,096 connections

3. The Architecture: Two-Tier Caching & Kernel Tuning

To break through loopback TCP contention and V8 serialization churn, we implemented the Two-Tier Hierarchical Caching Pattern:

Key Implementation Modules

1. In-Process L1 Micro-Cache (src/services/cache.service.js)

Each clustered worker process maintains its own localized in-memory Map with a 5-second micro-TTL: 

class CacheService {
  constructor() {
    this.l1Cache = new Map();
    this.L1_TTL_MS = 5000; // 5-second micro-cache absorbs 20k VU traffic spikes

    // Background expiration cleanup every 10 seconds (unreferenced to permit clean exit)
    setInterval(() => {
      const now = Date.now();
      for (const [key, item] of this.l1Cache.entries()) {
        if (now > item.expiresAt) this.l1Cache.delete(key);
      }
    }, 10000).unref();
  }

  getL1(key) {
    const item = this.l1Cache.get(key);
    if (!item) return null;
    if (Date.now() > item.expiresAt) {
      this.l1Cache.delete(key);
      return null;
    }
    return item.data;
  }
}

2. Distributed Stampede Mutex Lock (SETNX)

On dual cache misses, workers acquire a distributed mutex lock via Redis SETNX with atomic Lua script release. Exactly one worker queries MongoDB while concurrent requests spin-wait in memory for the warm cache, eliminating Thundering Herd stampedes entirely.

3. Diagnostic Response Headers

Responses carry diagnostic tiers for real-time observability: X-Cache: L1 ($1 mu ext{s}$), X-Cache: L2 ($0.2 ext{ ms}$), or X-Cache: MISS ($2.0 ext{ ms}$).

4. k6 Generator Optimization (discardResponseBodies: true)

Configuring k6 with discardResponseBodies: true prevents k6 from buffering 4.5+ GB of JSON in Go heap memory, reducing load-generator CPU consumption by ~70% and freeing CPU cores for Node.js worker execution.

5. Staff-Level System Design Interview Defense

Q1: "Why use Two-Tier L1/L2 Caching instead of pure Redis?"

"While Redis is an in-memory database, it communicates over network TCP sockets. At 20,000 concurrent clients, managing 40,000 local loopback sockets (HTTP + Redis) saturates OS kernel buffers and triggers massive CPU context-switching. An in-process V8 heap L1 cache serves 98% of repeated reads in 1 microsecond ($0.001 ext{ ms}$) without touching the network. Redis remains critical as the shared L2 layer to synchronize state across workers and prevent thundering herd stampedes on cold cache misses."

Q2: "How do you handle cache invalidation across clustered worker processes?"

"We utilize a hybrid invalidation strategy: 1. On transactional writes (POST /api/orders), the worker atomically writes to MongoDB and triggers non-blocking Redis SCAN eviction on L2 for affected catalog keys. 2. The executing worker flushes its local L1 cache immediately. 3. Other workers rely on a bounded 5-second micro-TTL on L1. Within 5 seconds, all worker processes automatically expire local RAM entries and fetch fresh inventory from L2 Redis."

Q3: "What kernel configurations are essential for ultra-high concurrency on Unix/macOS?"

"Three kernel parameters govern socket capacity: 1. Open File Limit (ulimit -n 65536): Sockets are file descriptors; default 256 limits will fail immediately under load. 2. Ephemeral Port Window (net.inet.ip.portrange.first=10240): Expands outbound ports from 16,383 to 55,295 to prevent EADDRNOTAVAIL. 3. Socket Listen Backlog (kern.ipc.somaxconn=4096): Expands kernel TCP accept queues to prevent connection drops during aggressive client ramp-ups."

Q4: "Why did you use MongoDB Replica Sets with secondaryPreferred?"

"In high-concurrency architectures, mixing heavy catalog search aggregation with transactional write operations creates disk IOPS contention on the primary database engine. By configuring a local replica set (rs0) and setting readPreference=secondaryPreferred, read traffic is offloaded to the secondary node (port 27018), reserving the primary node (port 27017) exclusively for ACID order placement and inventory decrements."

6. Engineering Conclusion

High concurrency is not achieved by applying caches indiscriminately; it requires understanding the full hardware, kernel, and runtime stack. By eliminating table scans via covered indexes, distributing load across 10 CPU cores, insulating the database via two-tier L1/L2 caching, and tuning OS socket backlogs, this backend demonstrated that Node.js can achieve enterprise-grade performance exceeding 7,300 requests per second with sub-2ms latency on a single machine.
